## P0/P1 confirmés

### [P0] ✅ CORRIGÉ — convert_abandoned_gauges double-mint : une seule recharge cash produit des items/crédits illimités (cost-basis recyclé + crédits re-mintés)
- **Fichier** : `supabase/migrations/20260616120004_fix_gauge_abandon_refund.sql` (l. 33-48)
- **Impact** : Une seule recharge Stripe permet de remplir des jauges (= obtenir des items physiques 'garantis' valant 2× le prix) en boucle, et re-minte ~1:1 les earned_credits dépensés. Cost-basis et crédits comptés deux fois : perte sèche illimitée (items expédiés + crédits gratuits) une fois GAUGE_ENABLED en prod et le cron actif. C'est le scénario exact 'avancer la jauge / gagner un item sans payer' via le nouveau convert_abandoned_gauges.
- **Fix** : Choisir UNE seule restitution, pas les deux. Soit (a) rendre uniquement le cost-basis cash (purchased_value_cents += progress) SANS re-créditer earned_credits (les crédits ont déjà été dépensés et valorisés), soit (b) re-créditer earned_credits SANS restaurer le cost-basis. La sémantique 'rien n'est perdu' = restituer la VALEUR une fois : rendre le cost-basis cash seul (réutilisable sur une autre jauge) est cohérent ; ajouter en plus des earned_credits double la valeur. De plus, tracer dans une table que cette progression a déjà été restituée (idempotence forte) et refuser de re-convertir une jauge dont la progression provient d'un cost-basis déjà restauré.

### [P0] ✅ CORRIGÉ — La légende de la jauge n'explique jamais le ×2 : l'utilisateur ne sait pas qu'il paiera le DOUBLE de la valeur de l'item
- **Fichier** : `src/components/game/ItemGauge.tsx` (l. 184-200 (GaugeCaption) ; cf. src/lib/utils/constants.ts:18 GAUGE_MULTIPLIER=2)
- **Impact** : L'utilisateur croit faire une bonne affaire (« garanti ») alors qu'il paie le double du prix marché. Information matérielle omise sur le coût réel d'une transaction en argent réel : risque de plainte consommateur (pratique commerciale trompeuse par omission) et fragilise la défense juridique du pivot « jauge » dont tout l'intérêt est la transparence du prix (mémoire cleekzy-gauge-pivot).
- **Fix** : Afficher explicitement le multiplicateur et le coût total cible dans GaugeCaption, ex. : « Remplie, tu auras misé {target/100}€ (2× la valeur de {itemName}) et il est à toi, garanti. » ou au minimum « Cible : {target}€ — soit 2× la valeur. Encore {remaining}€. ». Ne pas réduire l'info au seul reliquat « Encore X€ ».

### [P1] ✅ CORRIGÉ — Self-exclusion gate fails OPEN on Supabase error (responsible-gaming pause bypassable during DB hiccup)
- **Fichier** : `src/lib/selfExclusion.ts` (l. 7-16)
- **Impact** : During a Supabase degradation, a player who explicitly self-excluded (jeu responsable) can log back in, click on games, and purchase credits. This is the exact harm the self-exclusion feature exists to prevent, and it silently disappears precisely when the DB is unstable. Regulatory/compliance-sensitive (ANJ / 18+).
- **Fix** : Capture and fail CLOSED on error: `const { data, error } = await supabase.from('user_self_exclusion')...; if (error) { // treat as excluded or throw a typed error the caller blocks on }`. At minimum, on `error` return a sentinel that callers treat as 'cannot verify -> block action' rather than 'allowed'. Keep the existing not-found (data null, no error) path as 'not excluded'.

### [P1] ✅ CORRIGÉ — Conversion de jauge abandonnée : double-création de valeur (mint earned_credits + restauration du cost-basis) = crédits payants recyclables à l'infini
- **Fichier** : `Cleekzy/supabase/migrations/20260616120004_fix_gauge_abandon_refund.sql` (l. 36-39 (UPDATE profiles SET earned_credits = earned_credits + v_credits, purchased_value_cents = purchased_value_cents + r.progress))
- **Impact** : Boucle de valeur nette positive sans nouvelle dépense : (1) acheter un pack une fois (earned_credits + purchased_value_cents alimentés) ; (2) cliquer une jauge avec ces crédits payants (gratuit en termes de jeu : on a obtenu les clics) ; (3) attendre 90 j d'inactivité sur cette jauge ; (4) le cron rend les earned_credits ET le cost-basis. On peut re-dépenser, re-attendre, re-récupérer indéfiniment. Au-delà de la 1re recharge gratuite, c'est un détournement durable de l'économie (clics payants offerts) qui fausse aussi les classements/jackpot (basés sur total_clicks). Pas un vol de cash direct, mais perte de revenu récurrente.
- **Fix** : Choisir UNE seule conversion. Si l'avoir doit redevenir des crédits dépensables : faire `earned_credits += v_credits` SANS ré-ajouter purchased_value_cents (les crédits rendus retombent dans le flux normal, le cost-basis cash reste consommé). Si au contraire l'avoir doit rester du cash-basis ré-attribuable à une autre jauge : restaurer purchased_value_cents SANS minter d'earned_credits. Ne jamais faire les deux. Ajouter un test d'invariant : somme(earned_credits valorisés) + purchased_value_cents conservée à chaque conversion.

### [P1] GameCard runs a continuous requestAnimationFrame loop per card even for timer-expired/non-urgent games
- **Fichier** : `src/components/lobby/GameCard.tsx` (l. 66-83)
- **Impact** : Sustained ~10 re-renders/sec/card on the lobby grid. Combined with the bot interval churn this keeps the main thread busy continuously, drains battery, and causes scroll/animation jank on mobile. The work continues even for calm games that have minutes left, where a 1s tick (or no tick) would suffice.
- **Fix** : Gate the RAF/tick frequency on urgency: use a 1s setInterval for non-urgent games and only switch to ~100ms RAF when timeLeft <= FINAL_PHASE_THRESHOLD. Also stop the loop once timeLeft reaches 0 (isTimerEnded) so expired-but-not-yet-'ended' cards don't spin forever.
