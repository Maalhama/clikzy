## État par dimension

### Securite applicative (2)

Posture securite tres solide, fruit des durcissements successifs (audits 06-12/06-15/06-16/06-18). L authz est presente sur 100% des server actions admin (checkAdminStatus) ET re-verifiee cote DB (admin_set_credits/admin_set_admin re-checkent is_admin du caller via auth.uid()). Aucun IDOR : chaque RPC SECURITY DEFINER prend soit p_user_id avec le garde-fou `IF auth.uid() IS DISTINCT FROM p_user_id THEN RAISE forbidden`, soit scope par auth.uid() (open_chest/equip_item verifient user_id du proprietaire). Pas d injection SQL (zero EXECUTE/format dynamique dans les migrations). Pas de XSS exploitable (un seul dangerouslySetInnerHTML, JSON-LD 100% statique ; commentaires capes a 280 char et rendus via React auto-echappe). CSP par requete avec nonce, open-redirect garde dans /auth/callback, anti-spoof, fail-closed sur tous les crons (CRON_SECRET) et sur les rate-limiters sensibles (auth/paiement/clics). service_role jamais expose cote client, secrets jamais commit (.env gitignore, seules valeurs dummy en tests). Webhook Stripe : signature verifiee + idempotence + clawback complet. Le seul ecart reel restant est mineur : les rate-limiters d auth pour les flux non authentifies (signin/signup/reset) ne se basent que sur le 1er hop de x-forwarded-for.

### Chemin argent / Stripe (5)

Le chemin argent est globalement robuste et bien durci : webhook Stripe idempotent (claim sur stripe_events PK + ledger credit_grant_sessions par session, double defense), prix/credits TOUJOURS recalcules serveur (jamais le client), clawbacks complets (pack/gift/buy-it-now/battle-pass/VIP/cost-basis/gel gauge_wins), refund automatique des paiements sans contrepartie, et excellente couverture de tests (35+ scenarios). Les corrections du 2026-06-18 tiennent (REVOKE INSERT clicks, clawbacks etendus, CHECK>=0). Les problemes restants sont surtout operationnels et de fiabilite : gauge_wins (obligation argent reel — items gagnes via la jauge x2) n est lu par AUCUNE surface admin donc le fulfillment et le gel clawback sont inertes ; risque de double-souscription VIP (double facturation) ; et une TOCTOU benigne sur le flag de comptage de la jauge. Aucune faille de double-credit ou de manipulation de montant cote client trouvee.

### DB / RLS / migrations (5)

La couche données est globalement très bien durcie après plusieurs rondes d'audit : les 36 tables ont RLS activé avec des policies cohérentes (lecture publique whitelistée par GRANT colonne sur profiles/winners, écritures interdites côté client et routées via RPC SECURITY DEFINER service_role-only), les RPC DEFINER ont toutes search_path=pg_catalog,public dans leur état final, les gardes anti-IDOR (auth.uid()) et anti-TOCTOU (FOR UPDATE) sont en place, le trigger protect_profile_sensitive_columns est bien en SECURITY INVOKER et couvre toutes les colonnes monétaires/progression/équité, et les chaînes de migrations conflictuelles (gauge convert x3, protect trigger x6) convergent correctement par ordre lexical. Les éléments du 2026-06-18 (REVOKE INSERT clicks, clawbacks, CHECK>=0, etc.) tiennent. Le principal trou réel : un FK auto-référentiel referred_by sans ON DELETE qui CASSE silencieusement la suppression de compte RGPD pour tout parrain — oublié par la migration fk_delete_set_null qui visait justement à débloquer deleteMyAccount. Le reste est mineur (atomicité de l'écriture du gagnant hors transaction, colonne vip_subscription_id non protégée, lookups non indexés).

### Bugs logique / races / edge cases (7)

Le coeur "clic atomique" (perform_click) et la cloture (end_game) sont corrects et bien verrouilles (FOR UPDATE, revérif sous verrou, sequence_number atomique) ; la fairness, le mint de credits gratuits, les jauges et les clawbacks sont durcis et tiennent. En revanche le cron bot-clicks contredit la regle "dernier clic gagne" : il ecrase de maniere non gardee (UPDATE sans condition, depuis un snapshot perime) last_click_user_id/end_time/total_clicks, ce qui vole le lead a un vrai joueur (y compris en phase finale decisive) et perd des increments concurrents. Findings secondaires reels : rang periodique du joueur calcule avec l'XP all-time (faux), slots dont le paiement est decouple des symboles affiches (integrite du provably-fair), applyReferralCode et getItemGauge.completed avec petites races/incoherences.

### Performance React/Next (10)

Le projet montre une vraie maturite perf sur plusieurs points (timers adaptatifs au lieu de rAF permanent, GameCard/GameClicksFeed memoises, modales/framer en next/dynamic, optimizePackageImports, getCurrentUser via React cache, images next/image avec sizes partout, landing partiellement cachee via unstable_cache). Les problemes restants sont concentres sur (1) la duplication de requetes auth/profile cote serveur sur le lobby et la page jeu, (2) la redondance polling+realtime et des souscriptions realtime sans filtre qui inondent chaque client, (3) le re-render churn de la simulation de bots du lobby dont l effet se recree chaque seconde, (4) la page jeu monolithique client de 1159 lignes qui re-render integralement 4x/s en phase finale avec des enfants non memoises, et (5) des requetes SSR gachees (clics de la page jeu, query featured de la landing). Aucun bloqueur prod cote perf, mais des gains nets de TTFB et de fluidite sont possibles.

### SEO (8)

Le socle SEO est solide et inhabituellement soigné : metadata par page (title/description), template de titre, OG/Twitter file-based (opengraph-image.tsx, twitter-image.tsx, OG Wrapped dynamique), JSON-LD Organization+WebSite volontairement honnete (offers price 0 retire), sitemap.ts qui exclut les pages privees, robots.txt en Disallow, noindex sur le groupe (auth), focus sur cleekzy.com, lang=fr, locale fr_FR. Les problemes restants sont reels mais ciblés : (1) NEXT_PUBLIC_SITE_URL=localhost par defaut dans les .env, ce qui casse TOUS les canonicals/OG/sitemap si la prod ne l'override pas (var inlinee au build) ; (2) incoherence www vs non-www entre la base SEO (www) et auth/legal (non-www) ; (3) le copy meta « Jeu gratuit / gratuitement / lots gratuits » contredit le principe d'honnetete que l'equipe applique deja au JSON-LD ; (4) plusieurs pages legales sans canonical et pages privees indexables sans robots:index:false ; (5) pas de llms.txt ; (6) /joueur dans le sitemap sans canonical.

### Accessibilite (WCAG 2.2) (6)

L'accessibilité de Cleekzy est globalement solide et clairement durcie : le hook useModalA11y (focus initial + focus trap Tab/Shift+Tab + Échap + restauration du focus déclencheur) est correctement branché sur TOUTES les vraies modales (3 modals/, LobbyChests/Character, CaseOpening, RewardsCalendar, Jackpot, SpotlightTour, IOSInstallTour, PaymentSuccess), un SkipLink + landmark <main id="main-content"> existent, prefers-reduced-motion est respecté à la fois globalement (règle CSS blanket dans globals.css) et par composant (useReducedMotion framer), role="alert" est présent sur les erreurs de formulaire, le game-client expose des régions aria-live + role="timer", la nav a aria-expanded/haspopup/label, les formulaires ont labels+autocomplete, l'age-gate 18+ est accessible, et toutes les <Image> ont un alt. Les écarts réels restants sont localisés : deux overlays modaux non câblés au hook, des cibles tactiles de boutons fermer < 24px, et quelques textes text-white/35 sous le seuil de contraste AA.

### Legal / conformite (ANJ, RGPD) (10)

Les pages légales sont nombreuses et globalement soignées (CGU/CGV/mentions/privacy/jeu-responsable/comment-ca-marche), le 18+ est vérifié serveur, l'export/suppression RGPD existent et la jauge est documentée dans la privacy. Mais il subsiste des incohérences réelles entre le marketing et le modèle économique, des manques RGPD concrets (retrait du consentement cookies impossible, mentions légales incomplètes), et le risque ANJ central est aggravé par des affirmations contractuelles directement contredites par le code (CGU « pas un jeu de hasard » vs bots qui désignent des gagnants + jauge ×2). Le bloqueur ANJ de fond est déjà connu ; je donne ici des correctifs actionnables précis, page par page.

### Oublis produit / features manquantes (10)

Le coeur du produit (encheres, jauge, VIP, battle pass, mini-jeux, collection, clans, parrainage, RGPD) est complet et instrumente. Les vrais oublis sont operationnels et de confiance: (1) l'admin ne peut PAS creer/editer un lot ni programmer une partie depuis l'UI (createItem est du code mort, tout passe par des scripts dev) - bloqueur d'exploitation en prod; (2) aucune moderation (commentaires publics, pseudos, clans) - risque reel sur un produit argent reel public; (3) absence d'outils de jeu responsable concrets (pas de limite de depot/depense) et d'opt-out email; (4) plusieurs notifications manquantes (avoir jauge converti, relance adresse gagnant) et pas d'historique de transactions credits cote joueur. Cible: 7 features a fort levier ci-dessous.

### UX / parcours / mobile (9)

L'expérience est visuellement très soignée et cohérente (DA néon/dark, Unbounded/Hanken, focus-trap modales, états de chargement/vide/erreur complets, tours mascotte SpotlightTour/IOSInstallTour bien faits, accents FR irréprochables). Les vrais problèmes ne sont pas esthétiques mais éthiques/transparence : plusieurs dark patterns substantiels driveraient la conversion sur de la fausse urgence et de la fausse preuve sociale, et des incohérences de microcopy sur des écrans monétisés (mini-jeux à EV négative assumée, x2 promis sans condition, jauge cash sans montant en €, "100% gratuit" sur un produit payant). Ce sont des risques de confiance et de conformité (UCPD/DGCCRF) qui dépassent le simple polish.

### Qualite / code mort / types (8)

Le code est globalement bien structure (actions/lib/components separes, types derives via supabase gen, gestion d'erreur presente avec peu de catch vides). Mais la derive de typage est massive et systemique : 97 occurrences de `as any` dont 54 castent `.rpc as any` et 27 castent le client entier (`supabase as any`), annulant integralement le typage genere de `database.types.ts` (58 fonctions RPC pourtant typees). La cause racine est double : (1) `database.types.ts` est STALE — les tables phares de la jauge (`user_item_gauges`, `gauge_wins`) et plusieurs RPC (`get_my_winners`, `increment_item_gauge`, `convert_abandoned_gauges`, `add_purchased_value`) manquent, forcant des casts ; (2) un pattern de cast aveugle s'est generalise meme sur les RPC parfaitement types. S'ajoutent du code mort confirme (~236 lignes), une duplication DRY du type de resultat (16 declarations identiques sous 2 noms) et quelques trous de type evitables.

### Infra / observabilite / crons (8)

Le socle d'exploitation est globalement solide et a manifestement ete durci (Sentry scrub PII propre sur les 3 runtimes, rate-limit Redis fail-closed sur auth/paiement/clics, CSP par requete avec nonce, headers de securite complets, crons fail-closed sur CRON_SECRET, idempotence pensee). Les corrections du 2026-06-18 tiennent. ## P0 — 2 BLOQUANT

#### 1. Marketing « Jeu 100% gratuit • Aucun paiement requis » contredit le modèle argent réel (pratique commerciale trompeuse)

- **Sévérité** : P0 · **Statut** : ✅ confirmé · **Confiance** : high · **Dimension** : Legal / conformite (ANJ, RGPD)
- **Emplacement** : `src/components/landing/LandingClient.tsx:558, :655, :1191`
- **Problème** : La landing répète textuellement « Jeu 100% gratuit • Aucun paiement requis • Lots réels » à 3 endroits, et le CTA dit « JOUER GRATUITEMENT » (:552). Or le modèle entier repose sur de l'argent réel : la page jeu-responsable (src/app/(legal)/jeu-responsable/page.tsx:38-40) écrit elle-même « les crédits s'achètent avec de l'argent réel » et « Ne joue jamais avec de l'argent destiné à tes dépenses essentielles », et comment-ca-marche (:57-60) confirme la jauge où « tu auras misé 2× la valeur réelle de l'item en argent réel ». Affirmer « 100% gratuit / aucun paiement requis » alors que gagner un lot suppose en pratique d'acheter des crédits (les 10 gratuits/jour s'épuisent en 10 clics) est une allégation de gratuité prohibée.
- **Impact** : Pratique commerciale trompeuse au sens de l'art. L121-2 et L121-4 (allégation de gratuité, dissimulation du caractère payant) du Code de la consommation ; contradiction interne flagrante entre la landing et les pages légales du même site, exploitable par la DGCCRF/un plaignant. Aggrave aussi le dossier ANJ (publicité minimisant le risque financier).
- **Reco** : Supprimer « 100% gratuit » et « Aucun paiement requis » du hero et du dernier CTA. Remplacer par une formulation exacte : « Inscription gratuite + 10 clics offerts/jour ; crédits supplémentaires payants. Réservé aux 18 ans et plus. » Aligner le wording sur jeu-responsable. Garder « JOUER GRATUITEMENT » est acceptable seulement si la mention payante est immédiatement visible à proximité.
- **Vérif adversariale** : Code vérifié aux trois emplacements exacts signalés. 

- `LandingClient.tsx:558` : `<p className="text-[11px] text-white/55 ...">Jeu 100% gratuit • Aucun paiement requis • Lots réels</p>` — section hero mobile, sans aucun disclaimer adjacent.
- `LandingClient.tsx:655` : `<p className="text-sm text-white/45">Jeu 100% gratuit • Aucun paiement requis • Lots réels livrés chez toi</p>` — section hero desktop, sans aucun disclaimer adjacent.
- `LandingClient.tsx:1191` : même phrase mot pour mot dans le CTA final, immédiatement au-dessus du bouton "JOUER GRATUITEMENT" (:1211), sans mention du caractère payant des crédits.

En parallèle, `jeu-responsable/page.tsx:38-40` écrit explicitement "les crédits s'achètent avec de l'argent réel" et "Ne joue jamais avec de l'argent destiné à tes dépenses essentielles". La contradiction interne est directe et documentée dans le même site.

Aucun garde-fou dans le code adjacent ne vient nuancer l'affirmation "Aucun paiement requis". Les 10 crédits gratuits/jour s'épuisent en 10 clics (un clic = un crédit) ; obtenir un lot en pratique requiert des achats. L'affirmation "100% gratuit / Aucun paiement requis" constitue donc bien une allégation de gratuité au sens de l'art. L121-2 et L121-4 du Code de la consommation (pratique commerciale trompeuse).

La sévérité P0 est justifiée : risque DGCCRF concret, aggrave le dossier ANJ déjà ouvert, exploitable immédiatement par un concurrent ou un plaignant. Ce n'est pas du code mort — les trois occurrences sont dans des sections actives (hero mobile, hero desktop, CTA final).

#### 2. CGU « CLEEKZY n'est pas un jeu de hasard » contredite par les bots qui désignent des gagnants

- **Sévérité** : P0 · **Statut** : ✅ confirmé · **Confiance** : high · **Dimension** : Legal / conformite (ANJ, RGPD)
- **Emplacement** : `src/app/(legal)/terms/page.tsx:65 (vs src/app/api/cron/bot-clicks/route.ts:218-235)`
- **Problème** : Le CGU art. 4 affirme : « CLEEKZY n'est pas un jeu de hasard. Il n'y a pas de tirage au sort ni d'algorithme aléatoire. Le résultat dépend uniquement du timing des joueurs. » Le code dit l'inverse : le cron bot-clicks fait cliquer des bots pour prendre le lead (route.ts:218 `updates.last_click_username = botUsername; last_click_user_id = null`), maintient le timer pendant une « bataille » dont la durée est tirée pseudo-aléatoirement (simulation.ts:37-40 getBattleDuration via seed), et quand la bataille se termine sans joueur réel, laisse le timer tomber à zéro avec un bot en tête (route.ts:231 « battle_ended … no real player, letting timer run down »). L'issue dépend donc d'un paramètre opérateur pseudo-aléatoire et d'agents contrôlés par la plateforme, pas « uniquement du timing des joueurs ».
- **Impact** : Le triptyque mise en argent réel + espérance de gain + intervention du hasard/opérateur caractérise un jeu d'argent et de hasard (art. L320-1 Code de la sécurité intérieure). La clause CGU est non seulement fausse mais peut être retenue comme un aveu de tentative de contournement (élément aggravant ANJ et pénal — exploitation de jeu d'argent non autorisé). C'est le bloqueur légal connu, mais la rédaction de la CGU l'aggrave activement.
- **Reco** : Action propriétaire/avocat (ANJ) déjà identifiée. Côté code immédiat : NE PAS affirmer « pas un jeu de hasard » dans un texte contractuel — supprimer ou réécrire la clause art. 4 pour ne pas créer de fausse qualification juridique opposable. La décision de fond (modèle ×2 + bots gagnants) relève de l'avis avocat ANJ.
- **Vérif adversariale** : Les deux éléments clés sont vérifiés dans le code réel:

1. CGU art. 4 (`src/app/(legal)/terms/page.tsx:65`): "CLEEKZY n'est pas un jeu de hasard. Il n'y a pas de tirage au sort ni d'algorithme aléatoire. Le résultat dépend uniquement du timing des joueurs." — texte confirmé tel quel.

2. Code bot-clicks (`src/app/api/cron/bot-clicks/route.ts:218-236`): les bots prennent le lead (last_click_username = botUsername, last_click_user_id = null) aussi bien en phase normale (ligne 235-236) qu'en phase bataille finale (ligne 218-219). La durée de la bataille est déterminée par `getBattleDuration` dans `src/lib/bots/simulation.ts:37-40` via un hash de game_id (déterministe mais opaque pour les joueurs, fonctionnellement pseudo-aléatoire). La RPC `end_game` retourne `out_is_bot: boolean` (ligne 335), confirmant que les bots peuvent être déclarés gagnants.

Quand la bataille se termine sans joueur réel (ligne 231), le timer descend avec un bot en tête — le bot gagne la partie. Ce comportement contredit directement la clause CGU qui affirme que le résultat dépend "uniquement du timing des joueurs".

Le bloqueur légal/ANJ est déjà connu (indiqué dans les instructions). Ce finding documente spécifiquement la contradiction entre le texte contractuel CGU et le code opérationnel, ce qui constitue un risque aggravant autonome: la clause CGU crée une fausse qualification juridique écrite et opposable, indépendamment du problème ANJ sous-jacent. La sévérité P0 est correcte car il s'agit d'un texte contractuel potentiellement faux engageant la responsabilité pénale de l'opérateur.

## P1 — 14 sérieux

#### 1. Modale jeu mini-jeux : ni role=dialog/aria-modal, ni focus trap (useModalA11y absent)

- **Sévérité** : P1 · **Statut** : ✅ confirmé · **Confiance** : high · **Dimension** : Accessibilite (WCAG 2.2)
- **Emplacement** : `src/app/(main)/mini-games/MiniGamesClient.tsx:387-396`
- **Problème** : L'overlay de jeu (roue, scratch, pachinko, coinflip, slot) est rendu en plein écran avec `<div className="fixed inset-0 z-[100] ...">` mais SANS role="dialog", SANS aria-modal="true", SANS aria-label, et SANS appel à useModalA11y. Conséquence : pas de piège de focus (le Tab sort vers la page derrière), pas de fermeture à Échap, pas de restauration du focus sur le déclencheur, et le lecteur d'écran n'annonce pas qu'une boîte de dialogue modale s'est ouverte. Le backdrop (l.395) ne ferme qu'après résultat (`result && closeModal()`), donc pendant le jeu il n'y a aucun moyen clavier de fermer. C'est le seul vrai overlay du flux principal à ne pas suivre le pattern useModalA11y appliqué partout ailleurs.
- **Impact** : Utilisateurs clavier et lecteurs d'écran : focus perdu derrière la modale pendant le jeu, contexte modal non annoncé, pas de fermeture Échap. Viole WCAG 2.4.3 (Focus Order), 4.1.2 (Name/Role/Value), 2.1.2 (No Keyboard Trap inversé : le focus s'échappe).
- **Reco** : Aligner sur le pattern existant : ajouter `role="dialog" aria-modal="true" aria-label={GAME_CONFIG[activeGame].title}` sur le conteneur, un `panelRef` sur la card interne, et `useModalA11y(!!activeGame, closeModal, panelRef)` (en gardant la logique "fermeture seulement après résultat" si voulue, mais Échap doit au minimum être géré).
- **Vérif adversariale** : Le code réel à src/app/(main)/mini-games/MiniGamesClient.tsx:386-396 confirme le finding. L'overlay du jeu est un `<div className="fixed inset-0 z-[100]...">` sans `role="dialog"`, sans `aria-modal="true"`, sans `aria-label`, et sans appel à `useModalA11y`. Le hook `useModalA11y` (src/hooks/useModalA11y.ts) existe et gère focus trap, Échap, et restauration du focus. Il est utilisé dans TOUS les autres overlays du projet (CreditPacksModal, VIPSubscriptionModal, AnonGateModal, CaseOpeningModal, etc. — 12 fichiers au total). La `CreditPacksModal` est même rendue dans le même fichier MiniGamesClient.tsx et l'utilise correctement. L'overlay jeu est l'unique exception. Conséquences réelles vérifiées : (1) le Tab sort de la modale vers la page derrière pendant le jeu, (2) Échap ne ferme pas la modale (et pendant le jeu il n'y a pas de bouton X — le seul bouton X apparaît `{result && ...}`, donc pendant la phase active du jeu il n'y a aucun moyen clavier de fermer), (3) les lecteurs d'écran n'annoncent pas de contexte modal. La sévérité P1 est correcte : c'est un bug accessibilité sérieux sur un flux payant (crédits dépensés pour jouer), mais pas P0 car il n'y a pas d'exploitation financière ni de casse prod.

#### 2. FK referred_by -> profiles(referral_code) sans ON DELETE bloque la suppression de compte RGPD pour tout parrain

- **Sévérité** : P1 · **Statut** : ✅ confirmé · **Confiance** : high · **Dimension** : DB / RLS / migrations
- **Emplacement** : `supabase/migrations/20260123000004_referral_system.sql:5`
- **Problème** : Le FK auto-référentiel `ALTER TABLE profiles ADD COLUMN referred_by TEXT REFERENCES profiles(referral_code)` est créé SANS clause ON DELETE (donc NO ACTION par défaut) et n'est JAMAIS modifié par une migration ultérieure (vérifié : `grep referred_by ... REFERENCES|ON DELETE|fkey` ne retourne que cette ligne). Quand un joueur qui a parrainé au moins un filleul supprime son compte, deleteMyAccount() (src/actions/privacy.ts:96) appelle `svc.auth.admin.deleteUser(user.id)` qui CASCADE-supprime sa ligne profiles (FK profiles.id->auth.users ON DELETE CASCADE). Mais d'autres lignes profiles ont `referred_by = <referral_code du partant>` -> la suppression viole le FK NO ACTION -> erreur Postgres. Le code attrape l'erreur (delErr) et renvoie « Tes données ont été anonymisées mais la suppression finale a échoué ». La migration 20260615170001_fk_delete_set_null.sql annonce explicitement vouloir rendre la suppression « RÉELLEMENT possible » et corrige 5 FK vers profiles(id), mais a OUBLIÉ ce 6e FK qui pointe vers profiles(referral_code).
- **Impact** : Droit à l'effacement (RGPD art. 17) silencieusement cassé pour toute la cohorte de parrains (population qui grandit avec le programme de parrainage). L'utilisateur voit un échec, le compte d'auth/email n'est jamais supprimé. Risque de non-conformité RGPD + tickets support.
- **Reco** : Ajouter une migration : `ALTER TABLE profiles DROP CONSTRAINT profiles_referred_by_fkey; ALTER TABLE profiles ADD CONSTRAINT profiles_referred_by_fkey FOREIGN KEY (referred_by) REFERENCES profiles(referral_code) ON DELETE SET NULL;` (referred_by est nullable, on dé-identifie le lien de parrainage du filleul sans casser son historique). Vérifier le nom réel de la contrainte généré par Postgres.
- **Vérif adversariale** : Verification complète dans le code réel :

1. **FK incriminée confirmée** : `supabase/migrations/20260123000004_referral_system.sql:5` — `ALTER TABLE profiles ADD COLUMN IF NOT EXISTS referred_by TEXT REFERENCES profiles(referral_code);` — aucun `ON DELETE`, donc `NO ACTION` par défaut (PostgreSQL bloque si une ligne référencée est supprimée alors que d'autres lignes la référencent).

2. **CASCADE depuis auth.users confirmé** : `supabase/migrations/001_initial_schema.sql:10` — `profiles.id UUID PRIMARY KEY REFERENCES auth.users(id) ON DELETE CASCADE`. La suppression d'un utilisateur auth déclenche la suppression de son profil.

#### 8. Le cron bot-clicks vole le lead a un vrai joueur en phase finale (violation 'dernier clic gagne')

- **Sévérité** : P1 · **Statut** : ✅ confirmé · **Confiance** : high · **Dimension** : Bugs logique / races / edge cases
- **Emplacement** : `src/app/api/cron/bot-clicks/route.ts:204-248`
- **Problème** : En phase finale, quand le timer passe sous le seuil par-partie (clickThreshold 65-85s), le cron pose inconditionnellement updates.last_click_user_id = null (l.219) puis fait un UPDATE non garde (l.243-247: .update(updates).eq('id', game.id), aucune condition sur last_click_at/last_click_user_id). Si un vrai joueur detient le dernier clic et que le cron tire entre deux de ses clics, le bot lui prend le lead. end_game (20260615160001) cloture ensuite sur g.last_click_user_id, donc le gagnant autoritaire devient le bot (user_id=null, is_bot=true) alors que la regle est que le DERNIER clic humain gagne. perform_click verrouille bien la partie, mais le cron n'utilise PAS ce verrou ni de garde optimiste, donc son ecriture peut clobberer un perform_click qui vient de s'executer. C'est exactement la finding du 06-16 (docs/AUDIT-2026-06-16.md:182), restee OUVERTE (non re-traitee par 06-17/06-18).
- **Impact** : Un joueur qui a legitimement le dernier clic peut perdre l'enchere (argent reel) au profit d'un bot, uniquement a cause du timing du cron. Casse l'invariant central du produit et expose a un litige (issue alteree par un participant automatise de l'operateur).
- **Reco** : Rendre l'ecriture du cron conditionnelle : ne reprendre le lead que si aucun clic humain recent (ex. WHERE last_click_user_id IS NULL OR last_click_at < now()-Xs), ou faire passer l'activite bot par une RPC qui prend le meme verrou FOR UPDATE que perform_click et revérifie last_click_at avant d'ecraser. En phase finale, ne jamais ecraser un last_click_user_id non-null recent.
- **Vérif adversariale** : Verified in code. The race is real:

1. `perform_click` (supabase/migrations/20260609130001_perform_click_rpc.sql:28-29) acquires a `FOR UPDATE` row lock on `games` before writing `last_click_user_id = p_user_id`. This serializes concurrent human clicks correctly.

2. The cron update (src/app/api/cron/bot-clicks/route.ts:243-248) does a plain `supabase.from('games').update(updates).eq('id', game.id)` with no `FOR UPDATE`, no WHERE guard on `last_click_user_id` or `last_click_at`. It runs completely outside Postgres row-level locking.

3. In `final_phase` (lines 216-224), when `timeLeft <= clickThreshold`, the cron unconditionally sets `updates.last_click_user_id = null` and `updates.last_click_username = botUsername`. The `hasRealPlayer` check at line 202 is a snapshot read — not a database-level predicate. A human click that arrives between the cron's SELECT and the cron's UPDATE will be silently overwritten.

4. In normal phase (lines 235-237), same: `updates.last_click_user_id = null` is set unconditionally with no guard.

5. `end_game` RPC (20260615160001_audit_hardening.sql:43-63) does close correctly under `FOR UPDATE` and reads the authoritative `g.last_click_user_id`. But it only protects against the TOCTOU at closure time — it cannot undo a bot-click UPDATE that already clobbered a human winner after that human's `perform_click` committed and before `end_game` ran.

The attack window is: human clicks → `perform_click` commits (sets `last_click_user_id = human_uuid`) → cron fires within the same minute → cron reads snapshot where `last_click_user_id = human_uuid` but evaluates `timeLeft <= clickThreshold` → cron does unconditional UPDATE setting `last_click_user_id = null` → human loses lead → game ends with bot as winner.

No other guard in the codebase prevents this. The finding correctly identifies this as a violation of the "last human click wins" invariant, and the impact (real-money loss, operator-participant liability) justifies P1. The severity is correctly assessed.

#### 9. Souscriptions realtime du lobby sans filtre : chaque client recoit TOUS les clics et updates de toutes les parties

- Lignes 204-233 : souscription `postgres_changes` sur `event: 'INSERT', table: 'clicks'` sans aucun champ `filter:`. Comparaison : useGame.ts utilise correctement `filter: \`id=eq.${initialGame.id}\`` et `filter: \`game_id=eq.${initialGame.id}\`` — la bonne pratique est connue et délibérément absente du lobby.

La sévérité P1 est appropriée — pas de perte d'argent directe ni d'exploit, mais dégradation progressive de l'expérience utilisateur avec le trafic, particulièrement dommageable pour une PWA mobile.

## Réfutés / faux positifs (écartés par la vérif adversariale)

#### 1. gauge_wins (items physiques gagnes via la jauge x2 = obligation argent reel) n est lu par aucune surface admin — pas de fulfillment ni effet du gel clawback _(Chemin argent / Stripe, initial P1)_

- **Pourquoi écarté** : The finding claims that gauge_wins is read by "AUCUN read de gauge_wins" in src/ and that the clawback gel is "de facto inerte". Both claims are factually wrong after reading the code.

- src/actions/admin.ts lines 289-323: `getGaugeWins()` reads gauge_wins joined to profiles (with full shipping address: firstname/lastname/address/city/postal_code/country/phone) and to items (name), ordered by won_at, with pagination. This is exactly symmetric to `getBuyItNowOrders` for buy_it_now_purchases.
- src/actions/admin.ts lines 326-369: `updateGaugeWinShipping()` updates shipping_status/tracking_number on gauge_wins and sends a shipping email (sendShippingEmail), exactly like `updateBuyItNowShipping` for buy_it_now_purchases.
- src/actions/privacy.ts line 41: also reads gauge_wins for RGPD data export.

The clawback_hold status IS visible to the admin in the gauge_wins list (shipping_status is selected and returned). The query does not filter out clawback_hold rows — they appear in the admin list with their status. A minor gap is that there is no server-side guard preventing `updateGaugeWinShipping` from being called on a clawback_hold row (it would just update it), but this is an operational/UI concern, not a silent bypass — the admin sees the status and must manually avoid shipping held items.

The finding's core assertion ("AUCUN read de gauge_wins") is demonstrably false. The fulfillment surface exists and is functional.

#### 2. NEXT_PUBLIC_SITE_URL vaut localhost par defaut : tous les canonicals/OG/sitemap cassent si la prod ne l'override pas _(SEO, initial P1)_

- **Pourquoi écarté** : J'ai lu layout.tsx:51 et sitemap.ts:4. Les deux utilisent le pattern `process.env.NEXT_PUBLIC_SITE_URL || 'https://www.cleekzy.com'`. Le finding affirme que le fallback "ne sert à rien" parce que la var est déjà définie dans .env.example et .env.local. C'est faux pour deux raisons :

1. `.env.example` n'est jamais chargé par Next.js — c'est un fichier de documentation pure, sans effet sur les builds.
2. `.env.local` est un fichier de dev local, exclu du repo git (.gitignore) et non utilisé par Vercel en production. Les builds Vercel lisent uniquement les env vars définies dans le dashboard Vercel, pas .env.local.

Donc en production Vercel, si `NEXT_PUBLIC_SITE_URL` n'est pas définie dans le dashboard, la variable est `undefined` et le fallback `'https://www.cleekzy.com'` s'applique correctement. Le code est défensif et correct.

Le seul vrai risque résiduel serait qu'un opérateur ait explicitement configuré `NEXT_PUBLIC_SITE_URL=http://localhost:3000` dans les env vars de production Vercel — mais ce serait une erreur d'opération, pas un bug de code. Impossible à détecter depuis le repo. La sévérité P1 est sur-évaluée : au pire c'est une note P3 (documenter dans .env.example que la valeur prod est https://www.cleekzy.com), mais le code en lui-même est sain.
